Glossary and honesty labels

Palantir's vocabulary, the demo's vocabulary, and what each surface does and does not model

All sessions Investigate Build Oversight

The demos use Palantir's terms in the interface so that you can read Palantir's own documentation and the public reporting about it. This page maps those terms to the older names used in the demo code and to plain-language meanings, and explains the small label on every panel.

Everything in the demos is synthetic. No real person is modelled. Palantir product names are used to describe what the demos imitate; the demos are not Palantir software.

The three honesty labels

Every panel carries one of three labels. Click a label in the apps to land on its entry below.

Mirrors Foundry/Gotham

The behaviour follows a concept Palantir documents, and the entry links to the documentation. Example: markings are inherited down lineage.

Simplified

The concept is real, but the demo's implementation is a stand-in. Example: transparent scoring rules standing in for Search Around-style network expansion.

Teaching extension

The demo goes beyond what Palantir documents because it helps you see something. Example: row- and field-level provenance; Foundry's own lineage is dataset-level.

Actions, entity resolution and purposes

Terms introduced in Session 2. Each has its own anchor, so the apps and the guides can link to it.

Action type Palantir term
A named, permitted change to the Ontology, such as Add to watchlist or Unmerge person. It declares the object type it applies to, its parameters (with validation), which roles may run it, whether a Checkpoint comes first, and its effects. Every run is recorded as an Action with the values before and after. In the demo the Action types live in the Investigate seed (ontology.actionTypes).
Kinetic layer and writeback Palantir terms
Palantir describes the Ontology as a semantic layer (objects and links: the nouns) plus a kinetic layer (Actions: the verbs). Writeback is the part of an Action that changes something outside the Ontology, such as a message to another organisation's system. Here a writeback is only a line in that system's simulated inbox, but it shows that a click in an analysis tool can travel to a border desk or a bank.
External system
A system outside the platform that receives writebacks. The demo has three, all simulated: the border watch system (border-watch), the bank compliance desk (bank-compliance) and case management (case-management).
Candidate pair
Two Persons the pipeline kept apart but that might be the same individual. Only pairs that share something cheap to compare (the same surname, phone or address: this is called blocking) are scored. Each pair gets a score between 0 and 1: the sum of the weights of the signals it shows (same name +, shared route +, dates of birth differ −). The Resolution tab in Build lists every pair with its signals and weights.
Threshold
The score at or above which two candidates count as the same person. The default, 0.75, is what the pipeline did. Lowering it merges more pairs; above 0.75 nothing splits, because the pipeline's own rule-based merges are fixed in this build. The threshold is shared by Build and Investigate, and each change is logged. Who sets it, and who pays for a false merge, is the discussion.
Union-find merge
The way the browser turns pairs into people. Start with every Person on their own; for each pair that scores at or above the threshold, put the two groups together. Merging is transitive: if A matches B and B matches C, all three become one person, even if A and C look nothing alike. The merged person gets every property of its members, and a watchlisted member's risk tag wins. An Unmerge Action records a rejection for one pair, which then stays apart at every threshold.
Purpose rule
A rule about which purposes data may be combined for, written so that software can check it. Every dataset carries the purpose it was collected for (healthcare, border security, financial crime…) and a legal basis; the session carries the purpose the user states. Example, rule R2: Data collected for healthcare may not be combined with law-enforcement purposes.
Karlsruhe mode Teaching extension
A switch in the session strip that enforces the purpose rules. When it is off, nothing is blocked but each expansion, rule run and Action logs the purposes involved. When it is on, an operation that breaks a rule shows a red Blocked by rule R2 card with a Request exception button, and Build marks each transform that combines incompatible purposes with a red rule badge. Named after the seat of Germany's Federal Constitutional Court, whose February 2023 ruling on automated data analysis by the police is the discussion case. It does not mirror a Palantir feature.

Our abstraction of the BVerfG 2023 ruling's logic, not its text [to verify against the press release before teaching as the court's criteria].

Markings and roles

Markings say what a role needs in order to see a dataset, an object or a single property. A dataset derived from a marked dataset inherits the marking; only the data protection officer can remove one, and only after a Checkpoint.

MarkingLabelMeaning
RoleSees markingsPurposes

The roles are enforced in your browser. That makes them a model of access control, not access control: anyone can open the developer tools and read everything.
