# Build (Foundry-style) — Technical Specification

This document specifies the current implementation of **Build (Foundry-style)**, the Foundry-style app at `foundry-demo/` (called *Foundry Studio* before the Phase 1 redesign). Governance behaviour follows `context/PHASE1_CONTRACT.md`. It is intended as an engineering handoff and design reference for further development. The Gotham-style sibling app is specified separately in `TECHNICAL_SPEC.md`.

## 1. Purpose

The Foundry demo complements the Gotham demo by exposing the *pipeline* that produces the ontology, the *intermediate datasets* between raw sources and final ontology, and the *lineage* connecting any final ontology value back to the raw row(s) that produced it.

Where the Gotham demo asks "given the ontology, how do you investigate?", this demo asks "how did that ontology come to exist?"

Since Phase 1 it also shows **governance on the build side**: dataset purpose, legal basis and retention, **markings carried down lineage** (and their removal by the data protection officer behind a Checkpoint), and the role-dependent view of every dataset and object, all through the shared core in `core/`.

## 2. System goals

### 2.1 Functional goals

- Show a real pipeline DAG with executable transforms.
- Expose every intermediate dataset (raw, normalized, resolved, final) with schema, row count, and sample rows.
- Allow any ontology entity to be traced back to all contributing raw source rows, with per-field provenance.
- Embed the actual Python source of each transform in the inspector pane so students can read the real code.
- Cross-link to the Gotham demo so a single entity can be viewed in both contexts.
- Support both `starter` and `simulator` datasets through one static browser application, reusing the same synthetic data files as the Gotham demo.

### 2.2 Non-goals

- This is **not** a production data integration platform.
- This does **not** implement ontology branching, write-back to source systems, permissioned/purpose-based access, or real-time pipeline execution.
- This does **not** render the ontology relationship graph — that is the Gotham demo's responsibility.
- This does **not** support in-browser pipeline re-execution; the pipeline runs offline at build time only.

## 3. High-level architecture

```text
synthetic_data/*                         -> shared raw datasets (same as Gotham demo)
pipeline/lib.py                          -> Dataset/Transform/LineageRecord framework
pipeline/0X_*.py                         -> executable, student-readable transform scripts
scripts/build_foundry_seed.py            -> orchestrates the pipeline, embeds source code, writes seed.js
foundry-demo/index.html                  -> static shell
foundry-demo/seed.js                     -> bundled pipeline + lineage + entity payload
foundry-demo/app.js, js/app-*.js        -> application logic (no framework; split by tab)
foundry-demo/styles.css                  -> dark IDE-style presentation (Deep Culture black/green)
```

Runtime model:

1. Raw CSV/JSONL files are generated by the existing `scripts/generate_synthetic_sources.py` (not owned by this app).
2. `build_foundry_seed.py` loads the 5 pipeline scripts dynamically (step 01 reads six raw files plus `manifest.json`), runs each transform in order, captures lineage as a side effect of the `Transform` framework.
3. The orchestrator also reads each pipeline script's source code from disk and embeds it as a string on each transform descriptor.
4. The combined payload (DAG + datasets + lineage + final entities/edges) is emitted as JavaScript into `foundry-demo/seed.js`.
5. `foundry-demo/app.js` loads the payload into browser memory. All rendering and navigation run client-side.
6. UI state (active tab, selected IDs) is persisted in `localStorage`, keyed by dataset.

## 4. Repository structure

### 4.1 Pipeline framework

- `pipeline/lib.py`
  - `Dataset(name, rows, source_file=None, schema=None)`
  - `LineageRecord` — maps output row indices to source row references; also stores per-field provenance
  - `Transform(name, description, inputs, fn)` — `run()` returns `(output_dataset, lineage_record)` and applies the marking union rule to the output
  - `Dataset.markings`, `.marking_provenance`, `.purpose`, `.legal_basis`, `.retention_days`, `.input_purposes`, `.derived_from`; `inherit_markings(output, inputs)` — the union rule, used by `Transform.run()` and by steps 02–05 (which build their datasets directly)
  - `slug(value)` — identical implementation to the Gotham demo's slug function, ensuring entity IDs match
- `pipeline/resolution.py` — the shared `PersonResolver` (`passport → phone → name+dob → alias`, `get_or_create()`, `find()`, `person_for()`, `resolutions()`), used by both step 02 and `scripts/build_ontology_seed.py`; also defines the fixed per-method confidences for the `resolution` block
- `pipeline/resolution.py` also provides `attach_clinic_rows()` / `PersonResolver.attach()` (Phase 1): clinic rows join an existing Person by exact name + dob, never create one, and change no key, name or `mergedFrom`
- `pipeline/governance.py` — markings, roles, purposes, checkpoints, honesty labels (`governance_block()`), manifest defaults (`SOURCE_DATASETS`), the dataset union rule (`derived_governance`) and object/link marking rules (`annotate_objects`); shared by both seed builders and the generator
- `pipeline/leads.py` (Phase 3) — the one address-confidence scorer (`compute_leads()`, `score()`, `FORMULA`, `SOURCES`, `GAZETTEER`), shared by step 06 and `scripts/build_ontology_seed.py`, so both seeds hold the same leads (§5.2)
- `pipeline/seedmeta.py` — seed versioning: `schemaVersion`, deterministic `buildId`, per-source hashes, `builder` label (used by both seed builders)

### 4.2 Pipeline scripts

The six transforms are executable Python modules. Filenames begin with a digit (e.g., `01_normalize_sources.py`) to make the execution order obvious; this makes them non-importable via normal `import` syntax, so the build script loads them via `importlib.util.spec_from_file_location`.

- `pipeline/01_normalize_sources.py` — reads the six raw files (`normalize_clinic()` for `clinic_registrations.csv`, optional); strips whitespace, parses dates to ISO strings, splits pipe-delimited fields, tags each row with `_source_row` (its original 0-based index in the raw file), and copies `markings`, `purpose`, `legalBasis`, `retentionDays` and `asOf` from `manifest.json` (`markingProvenance` = the raw file). `source_file` is the repo-relative path under the dataset directory passed in.
- `pipeline/02_resolve_persons.py` — entity resolution with the shared `PersonResolver` (priority `passport_id → phone_number → name+dob → alias`), in one greedy pass over watchlist, registry, flights and pings; then clinic rows attach by name + dob only and the latest supplies `homeAddress` / `clinicCode`. Captures per-field provenance and a `resolution` column; attaches the resolver to its output so step 05 links edges with the same state. Bank transactions are not an input (no bank field reaches a Person), so `resolved_persons` does not inherit `FIN`.
- `pipeline/03_resolve_companies.py` — deduplicates company registry rows by `company_id`.
- `pipeline/04_resolve_accounts.py` — extracts unique bank accounts from both sides of transactions.
- `pipeline/05_build_ontology.py` — produces Device, Flight, Airport, Location (including residential Locations from attached clinic rows), WatchlistRecord entities and all 13 edge types (`RESIDES_AT` with `{asOf, source}` is new), then marks every object, property and link (`governance.annotate_objects`). Person edges use the shared resolver: record-derived edges (LISTED_ON, DIRECTS, BENEFICIALLY_OWNS, BOOKED_ON, USES_DEVICE) go to the person the record was resolved into; OWNS_ACCOUNT matches the owner name against the final resolver state. The result has the same entity IDs and `(type, source, target)` edge set as the Gotham seed.
- `pipeline/06_build_leads.py` (Phase 3) — wraps `pipeline/leads.py` as a `lib.Transform` (`build_leads`, output dataset `leads`), with row- and field-level lineage for every lead (§5.2).

### 4.3 Build orchestrator

- `scripts/build_foundry_seed.py`
  - runs the pipeline for both `starter` and `simulator`
  - reads each `pipeline/0X_*.py` file's source as a string and attaches it to the corresponding transform descriptor
  - writes `foundry-demo/seed.js` as `window.foundrySeedCatalog = {...}` plus a default `window.foundrySeed` pointer

### 4.4 Demo UI

- `foundry-demo/index.html` — static entry point; loads the shared core, then `seed.js`, then `app.js` (§9.1). Does not load Leaflet.
- `foundry-demo/app.js` and `foundry-demo/js/app-*.js` — the Build app, split by tab (review F-24): `app-state.js` (helpers, UI state, derived helpers), `app-governance.js`, `app-shell.js` (render root, header, tabs, sidebar), `app-pipelines.js`, `app-datasets.js` (with the retention clock), `app-leads.js`, `app-lineage.js`, `app-markings.js`, `app-purposes.js`, `app-resolution.js`, and `app.js` (shared strips, event delegation, `init()`). No framework, no modules: they are classic scripts loaded in that order and share one global script scope, so a top-level function, `const` or `let` in one file is visible in the others. Only `app-state.js` (UI state) and `app.js` (`init()`) run code at load.
- `foundry-demo/styles.css` — dark IDE-style presentation in the Deep Culture palette. Shared fonts and colours come from `brand/deep-culture.css`.

## 5. Pipeline DAG

The pipeline has 6 transforms operating over 18 datasets (6 raw + 6 normalized + 3 resolved + 2 ontology + `leads`).

```text
watchlist.csv                ──┐
company_registry.csv         ──┤
flight_manifests.csv         ──┼─→ normalize_sources ─┬─→ norm_watchlist            ─┬─→ resolve_persons   ─→ resolved_persons   ─┐
bank_transactions.csv        ──┤                      ├─→ norm_company_registry     ─┼─→ resolve_companies ─→ resolved_companies ─┤
mobile_location_pings.jsonl  ──┤                      ├─→ norm_flight_manifests     ─┤                                            │
clinic_registrations.csv     ──┘                      ├─→ norm_bank_transactions    ───→ resolve_accounts  ─→ resolved_accounts  ─┼─→ build_ontology ─→ ontology_entities
                                                      ├─→ norm_mobile_pings         ─┤                                            │                  └─→ ontology_edges
                                                      └─→ norm_clinic_registrations ─┘                                            │
                                                            (all norm_* also feed build_ontology) ───────────────────────────────┘

resolved_persons + norm_clinic_registrations + norm_mobile_pings + norm_company_registry ─→ build_leads ─→ leads
```

Each normalized dataset is derived from its own raw file only (`derivedFrom: ["<file>"]`); `normalize_sources` is one logical step over six independent normalisations.

Transform inputs and outputs (as recorded in the seed):

| Transform | Inputs | Output |
|---|---|---|
| `normalize_sources` | 6 raw files | `norm_sources` (logical group covering 6 normalized datasets) |
| `resolve_persons` | `norm_watchlist`, `norm_company_registry`, `norm_flight_manifests`, `norm_mobile_pings`, `norm_clinic_registrations` | `resolved_persons` |
| `resolve_companies` | `norm_company_registry` | `resolved_companies` |
| `resolve_accounts` | `norm_bank_transactions` | `resolved_accounts` |
| `build_ontology` | all 3 resolved + all 6 `norm_*` | `ontology` (produces `ontology_entities` and `ontology_edges`) |
| `build_leads` | `resolved_persons`, `norm_clinic_registrations`, `norm_mobile_pings`, `norm_company_registry` | `leads` |

### 5.1 Markings down the DAG (Phase 1)

Raw datasets take their markings from `manifest.json`; every other dataset gets the union of the datasets in its `derivedFrom`, and `markingProvenance` records, per marking, the raw dataset(s) it came from. Result (both profiles):

| Dataset | Markings |
|---|---|
| raw / `norm_*` | `watchlist` LE-SENSITIVE · `company_registry` OPEN · `flight_manifests` PII · `bank_transactions` FIN · `mobile_location_pings` TELECOM · `clinic_registrations` PII, HEALTH (PII since the fix round) |
| `resolved_persons` | OPEN, PII, TELECOM, HEALTH, LE-SENSITIVE |
| `resolved_companies` | OPEN |
| `resolved_accounts` | FIN |
| `ontology_entities`, `ontology_edges` | all six |
| `leads` | OPEN, PII, TELECOM, HEALTH, LE-SENSITIVE (PII and LE-SENSITIVE come through `resolved_persons`) |

Since the fix round `clinic_registrations` is also PII, so `markingProvenance.PII` of every dataset downstream of it includes `clinic_registrations.csv`; no dataset's marking list changes (they all held PII already), and a HEALTH removal leaves them PII-marked. `company_registry.csv` and `norm_company_registry` carry `fieldMarkings: {beneficial_owner: ["PII"], beneficial_owner_dob: ["PII"]}` and a `fieldNote` (*WM and Sovim*); the datasets stay OPEN.

`HEALTH` reaches **5** datasets downstream of `clinic_registrations.csv`: `norm_clinic_registrations`, `resolved_persons`, `ontology_entities`, `ontology_edges`, `leads` (6 with the raw dataset itself). The spec's "7" assumed a longer DAG. Derived datasets get `purpose: "financial-crime"`, `legalBasis` "Not recorded …", `inputPurposes` (the purposes of everything upstream) and `retentionDays` = the shortest input retention.

### 5.2 Leads (Phase 3, F8)

`06 Build Leads` makes **one lead per Person with at least one address source** (PHASE3_CONTRACT.md §1): starter 24 leads (every Person), simulator 191 (every Person). Each source contributes at most one component, its most recent usable record:

| source dataset (`component.source`) | marking | weight | address used | date used |
|---|---|---|---|---|
| `norm_clinic_registrations` | HEALTH (`markings`: PII, HEALTH) | 0.5 | `home_address` of the latest attached registration | `registered_on` |
| `norm_mobile_pings` | TELECOM | 0.4 | the residential location if any ping is residential, else the most frequently observed non-airport location (ties: more recent, then label) | latest ping `timestamp` at that location |
| `norm_company_registry` | OPEN | 0.3 | `registered_address` of the most recently incorporated company the person directs or owns | `incorporation_date` |

`score = 100 · min(1, Σ weight_i · exp(−ageDays_i / 365))` (the exact string is stored as `formula`). `ageDays` = whole days from the record's date to `asOf`, the latest date in the step's inputs (`2026-04-12` in both profiles), so a rebuild gives the same numbers. `decay` is rounded to 4 decimals, `contribution` (= `100 · weight · decay`, in points) and `score` to 1 decimal. The best address is the component with the largest contribution. Persons are matched to records with the shared resolver (clinic rows by name + dob; pings and registry rows by `person_for(ref)`), exactly as step 05 links them.

Coordinates: clinic rows and pings carry `lat`/`lon`. The registry does not, so a registered address takes the coordinates of the same label in the clinic or ping data, else a small gazetteer in `pipeline/leads.py` (approximate street positions for the synthetic registry addresses; reference data like step 05's airport table, cited in lineage as `pipeline/leads.py:GAZETTEER`).

Lead shape (identical in `leads.sampleRows` here and in the Investigate seed's `leads.items`, TECHNICAL_SPEC.md §7.1e):

```js
{id: "lead::<personId>", personId, address, lat, lon, score, status: "open",
 components: [{source, marking, markings, weight, ageDays, decay, contribution, address,
               // markings (fix round): clinic ["PII","HEALTH"]; registry via beneficial owner ["OPEN","PII"]; else [marking]
               // additions to the contract shape:
               label, rawSource, purpose, date, lat, lon, record, pingCount?, companyId?, role?}],
 formula, asOf,
 addressSource,       // component.source of the best address
 sourceMarkings}      // union of the components' markings
```

The `leads` dataset entry adds `formula`, `decayDays: 365`, `weights` (the table above), `objectType: "Lead"`, `properties` (lead fields for the Close lead Action), `asOf`, and `rowLineage: {leadId: {sourceRows, fieldProvenance}}` for the sample rows. Sample rows are the **top 50** leads (sorted by score, then person ID); the Investigate seed carries all of them. Field provenance: `id`/`personId` → `resolved_persons` row (plus the matching name/dob or phone cells); `address`, `lat`, `lon` → the best component's cells; `score` → each component's date cell; `components[i]` → that component's address, date and coordinate cells.

The designed outcome (tested in `tests/test_leads.py`): in starter the namesake `person::g5510077` is the top lead (85.8 = clinic 45.9 + pings 39.9). Without HEALTH his lead falls to 39.9 at the street-level ping address "Oak Lane, Birmingham", and `person::elias-silva-1984-12-24` (56.2) is top. The three namesake pings (`PG-0101`–`PG-0103`, appended in Phase 3) locate the street, not the house, so the HEALTH-marked residential Location never collides with a ping location.

## 6. Lineage model

The `Transform.run()` method returns both the output dataset and a `LineageRecord`. For each output row, the LineageRecord stores:

- which input dataset(s) and row indices contributed
- the transform that produced the output
- per-field provenance: for each output field, the list of `{dataset, row, field, note}` references that produced its value

The build orchestrator keys the lineage by entity ID (e.g., `person::p8842101`) for the entities emitted by `build_ontology`. Earlier-stage lineage is captured but only the entity-level view is exposed in the UI.

Lineage payload shape (per entity):

```js
{
  "person::p8842101": {
    producedBy: "resolve_persons",
    sourceRows: [
      { dataset: "norm_watchlist", row: 0 },
      { dataset: "norm_flight_manifests", row: 0, note: "alias 'Karim Haddad' merged via passport" },
      { dataset: "norm_flight_manifests", row: 5 },
      { dataset: "norm_bank_transactions", rows: [0, 6, ...] }
    ],
    fieldProvenance: {
      canonicalName: [{dataset: "norm_watchlist", row: 0, field: "subject_name"}],
      aliases:       [{dataset: "norm_flight_manifests", row: 0, field: "passenger_name", note: "alias merged"}],
      passportId:    [{dataset: "norm_watchlist", row: 0, field: "passport_id"}],
      riskTag:       [{dataset: "norm_watchlist", row: 0, field: "risk_category"}]
    }
  }
}
```

## 7. Identity convention

Entity IDs are generated by the pipeline as:

```text
{type_lowercase}::{slug(external_key)}
```

This format is **identical** to the Gotham demo's identity convention (see `TECHNICAL_SPEC.md §10.1`) so that cross-links between the two apps land on the same entity. Example: `person::p8842101` is Kareem Haddad in both apps.

## 8. Seed payload contract

The browser consumes a per-dataset payload with this top-level shape:

```js
{
  metadata: {
    schemaVersion: 3,
    buildId: "sha256:<hex>",      // deterministic; see below
    sources: { "watchlist.csv": "sha256:<hex>", ... },
    builder: "build_foundry_seed.py@<git short sha or 'dirty'>",
    title, dataset, generatedAt
  },
  governance: {...},   // identical to the Gotham seed's (TECHNICAL_SPEC.md §7.1b), incl. Phase 2 purposeRules, legalBasisNote, discussions
  ontology: {          // Phase 2: only these two keys (TECHNICAL_SPEC.md §7.1d)
    actionTypes: [...], externalSystems: [...]
  },
  resolution: {...},   // Phase 2: candidate pairs for the Resolution tab (TECHNICAL_SPEC.md §7.1c, §8.8)
  pipeline: {
    transforms: [
      { id, name, description, inputs: [datasetId], output: datasetId,
        codePath, code, rowsIn, rowsOut }
    ]
  },
  datasets: [
    { id, name, sourceFile, schema: [{field, type}],
      rowCount, sampleRows: [...], producedBy, consumedBy: [...],
      derivedFrom: [datasetId],                 // [] for raw datasets
      markings: ["PII", ...],                   // union rule, §5.1
      markingProvenance: {HEALTH: ["clinic_registrations.csv"], ...},
      purpose, legalBasis, retentionDays, inputPurposes,
      fieldMarkings?, fieldNote?,               // company_registry.csv, norm_company_registry (fix round)
      asOf }                                    // raw, norm_* and leads
    // Phase 3: the `leads` entry also has formula, decayDays, weights, objectType,
    // properties and rowLineage (§5.2)
  ],
  lineage: {
    "<entity-id>": {
      producedBy, sourceRows: [...], fieldProvenance: {...}
    }
  },
  entities: [...],   // same shape as Gotham demo's seed entities, incl. markings, propertyMarkings, sourceMarkings
  edges: [...]       // same shape as Gotham demo's seed edges, incl. markings
}
```

Object, property and link markings follow `TECHNICAL_SPEC.md §7.3–7.4` and are identical in both seeds.

`buildId` hashes the dataset's raw source files including `manifest.json` (sorted, line endings normalised to LF), `scripts/build_foundry_seed.py` and every `pipeline/*.py`; it contains no timestamp, so an unchanged input set always gives the same `buildId` (REDESIGN_SPEC §6.2).

Person entities carry a top-level `resolution` block, identical to the Gotham seed's (`TECHNICAL_SPEC.md §7.3`, §8.1): `{method, confidence, mergedFrom, splitRisk, note}`. The same object appears in the `resolution` column of the `resolved_persons` dataset. For ping-only persons, `canonicalName` is the most frequent observed name and its field provenance is noted `"from ping observed_name (weak)"`.

`resolution` (Phase 2) is computed from the step-02 resolver after the pipeline runs (`pipeline/candidates.py`) and is identical to the Gotham seed's: `{defaultThreshold: 0.75, minThreshold: 0.30, fixedNote, signals, candidates}`. It is not a dataset in the DAG, so it adds no lineage node and the markings table in §5.1 is unchanged. No candidate reaches 0.75: the default threshold is exactly the pipeline's own Persons. The namesake pair `cand-n5538219--g5510077` scores 0.55; the simulator adds two namesake pairs at 0.50 and 0.60.

### 8.1 Bundled seed catalog

`foundry-demo/seed.js` exports:

```js
window.foundrySeedCatalog = { starter: {...}, simulator: {...} };
window.foundrySeed = window.foundrySeedCatalog["starter"];
```

### 8.2 Embedded transform code

Each transform descriptor includes a `code` field containing the actual UTF-8 source of the corresponding `pipeline/0X_*.py` file, read at build time. This avoids duplicating the transform code between the executable scripts and the UI. The codePath field records the original file path for traceability.

## 9. Application runtime model

The application is a static client-side SPA implemented without a framework.

### 9.1 Entry point

`foundry-demo/index.html` loads, in order (all classic scripts on `window.DC`):

1. `../core/store.js` — namespaced, versioned `localStorage` (`DC.store`)
2. `../core/governance.js`, `../core/session.js`, `../core/audit.js`, `../core/markings.js`, `../core/checkpoints.js`, `../core/purposes.js`, `../core/resolution.js`, `../core/actions.js`, `../core/ui.js` — the shared governance core (PHASE1_CONTRACT §6, PHASE2_CONTRACT §6), in that order, plus the stylesheet `../core/core.css`
3. `seed.js`
4. `js/leads.js` and `js/retention.js` — pure helpers (Phase 3) on `window.BuildLeads` and `window.BuildRetention`; no DOM, no core calls
5. `app.js`

On start the app calls `DC.governance.init(seed.governance)` with the first dataset key that carries a governance block, and again with the active dataset's block on every dataset switch (review F-18). Limitation: marking overrides and `ontologyRemoved` in `dc-palantir:governance` carry no dataset key, so a removal made while viewing starter also applies to simulator (both seeds have the same dataset ids and DAG, so the recomputed `ontologyRemoved` is the same either way). It then initialises the Phase 2 modules for the active dataset (again on every dataset switch), each only when present:

- `DC.purposes.init(seed.governance.purposeRules)`
- `DC.resolution.init(seed.resolution)` (also accepted at `seed.ontology.resolution`)
- `DC.actions.init(seed.ontology.actionTypes, seed.ontology.externalSystems)` — only when the Build seed carries Action types; otherwise Build offers Unmerge as a link to Investigate (§10.7)

**Graceful degradation.** Every core call goes through a guard (`core(name, fn)`, `safe(label, fn, fallback)`): when a core file is missing, a function is absent or throws, or the seed has no `governance` block, the app keeps working as the Phase 0 app. The session and audit strips stay hidden, nothing is logged, no role redaction is applied, the Markings tab is hidden unless datasets carry `markings`, and the Remove marking button is hidden unless both `DC.checkpoints.withCheckpoint` and `DC.markings.removeMarking` exist. A failing core call logs one `console.warn`, never an error.

Phase 3 degrades the same way. Without a leads dataset (no dataset with id `leads`, a producing transform named `*lead*`, or lead-shaped sample rows) the Leads group, the leads view and the lead entries on the Lineage tab simply do not appear. Without `DC.ui.leadFormula` the formula is rendered locally from `components`. Without the `build.retention` honesty entry the clock shows a built-in *Simplified* chip linked to `glossary.html#build.retention`. Without any dataset `asOf` (or without `js/retention.js`) the retention clock is hidden.

Phase 2 degrades the same way. Without `seed.resolution` the Resolution tab is hidden. With the seed block but without `core/resolution.js`, the tab runs on a local copy of the union-find (same representative rule as the contract); the slider then applies to this page only, is not shared with Investigate, and the page says so. Without `core/purposes.js` no rule badges or Karlsruhe panel appear. Without `DC.ui.discussionCardsFor` the discussion cards are rendered from `seed.governance.discussions` with simpler markup.

### 9.2 State model

Primary runtime state:

- `catalog` — the full `window.foundrySeedCatalog`
- `seedData` — the active dataset's payload (`catalog[ui.datasetKey]`)
- `ui` — `{ datasetKey, activeTab, selectedTransformId, selectedDatasetId, selectedEntityId, lineageEntitySearch, datasetRowOffset, markingFilter, selectedPersonId, resPreview, highlightDatasetRow }` (`resPreview` is the threshold shown while the slider is dragged; not persisted)
- the resolution threshold comes from `DC.resolution.threshold()` (stored by the core in `dc-palantir:governance.threshold`, shared with Investigate); resolution overrides from `DC.resolution.overrides()`, falling back to `dc-palantir:governance.resolutionOverrides`; Karlsruhe mode from `DC.purposes.enabled()`
- the current role comes from `DC.session.get().role`; marking overrides from `dc-palantir:governance` (read through `DC.markings`)

### 9.3 Persistence

UI state (selections, active tab, search box, row offset) is persisted in `localStorage` through `core/store.js` under the key:

```text
dc-palantir:foundry:{datasetKey}     {schemaVersion, buildId, data: {activeTab, selectedTransformId, …}}
```

The envelope is versioned against the seed (`metadata.schemaVersion` / `metadata.buildId`, or a fallback fingerprint of `pipeline.generatedAt` plus counts when the seed has no `metadata` block — see the Gotham spec §11.3). When the seed was regenerated or its schema changed, the saved UI state is reset silently (no banner, no stale copy kept). The pre-redesign key `foundry-studio-demo-v1:{datasetKey}` is removed on first load and its contents are not reused.

Shared governance state is owned by the core and shared with Investigate and Oversight:

```text
dc-palantir:session      {sessionId, role, purpose, flags}
dc-palantir:audit        [event…]
dc-palantir:governance   {markingOverrides: [{datasetId, removed, by, checkpointRecordId, ts, buildId}],
                          threshold, resolutionOverrides: [{candidateId, decision: "reject", by, reason, ts}],
                          actionLog: [...]}            (Phase 2 fields written by the core)
```

Build re-renders on `DC.session.onChange` (role changes, also from another tab), on a `storage` event for `dc-palantir:governance` (threshold, overrides and markings changed in Investigate), on `onChange` of `DC.purposes` / `DC.resolution` / `DC.actions` when the core offers it, and after any `change` inside the session strip (the Karlsruhe toggle lives there).

The seed data itself is **not** persisted — it is reloaded from `seed.js` on every page load. This is the opposite of the Gotham demo, which persists the whole ontology to allow inline editing. Foundry treats the pipeline as authoritative; the only mutable state is which view the user is currently looking at.

### 10.7 Resolution tab (F6)

Shown when the seed carries `resolution` (PHASE2_CONTRACT §2). Honesty chip `build.resolution`.

- **Left sidebar:** every Person that appears in a candidate pair, highest-scoring pairs first; selecting one opens its merge explanation.
- **Threshold slider:** `resolution.minThreshold` (0.30) to 0.95, step 0.01, default `resolution.defaultThreshold` (0.75), with presets 0.55, 0.65 and 0.75. Only the financial-crime analyst and the DPO may move it (fix round): the rule is read from a core predicate (`DC.resolution.canSetThreshold` or similar) when present, else role flags or `thresholdRoles` in the seed, else that list. Other roles see the slider and presets disabled with a *read only* tag and the reason. Build passes the risk-tagged Persons to `DC.resolution.init(block, {watchlisted})`, so the cluster representative is the watchlisted member, as in Investigate. Dragging (`input`) re-renders only the results under the slider (`#res-results`), so the slider survives the drag; releasing (`change`) or a preset commits through `DC.resolution.setThreshold(t)`, which persists and logs, and the whole page re-renders. Above the default a note says that the pipeline's deterministic merges are fixed in this build.
- **Counts:** Persons at the current threshold vs at the default, the difference, and the number of merges. Persons = Person objects in the seed minus (cluster size − 1) for every merged cluster.
- **People who changed identity at this threshold:** every cluster whose membership differs from the default, with its representative and, when the representative has a `riskTag` the role can see, which members inherit it.
- **Candidate pairs table:** left, right (names read through the role's redaction; auditor and contractor see "withheld — PII"), score, signals with weights (negative weights in red), and the decision at the current threshold: `merged` (in `resolveAt(t).merges`), `separate`, `same person via another pair` (transitive merge), or `rejected by override` (an override in `resolutionOverrides`, with who and why; honoured at every threshold).
- **The scorer's weights:** the full `resolution.signals` table (id, signed weight, label, note), so students can argue with it, followed by `resolution.note` (or `discussion`) as a Discussion line: there is no passport-conflict signal.
- An override's free-text reason is shown only to roles that can see both persons ("reason withheld" otherwise).
- **Merge explanation** (right column, sticky): for the selected Person, its cluster at the current threshold and the merge chain from `DC.resolution.explain(personId)` (falling back to the merged pairs of its cluster). Each pair shows the arithmetic, one row per signal (`+0.45 name-exact`, `+0.20 shared-route`, `−0.10 dob-conflict`) and the total (`= 0.55`, clamped to 0–1, with a warning if the seed's score differs from the sum), the verdict against the threshold, and the candidate's plain-English `explanation` (only when the role can see both persons). Pairs that do not merge are listed with "would merge at *score* or lower".
- **Unmerge:** each merged pair offers *Unmerge in Investigate →*, a deep link `../demo/index.html#object=<representative>&dataset=<key>` where the Action runs. When `DC.actions` is loaded with an `act-unmerge-person` type that the current role may run (`DC.actions.applicable("Person", role)`), Build also shows the Action's parameters (the candidate id is filled in) and an Unmerge button that calls `DC.actions.applyAction("act-unmerge-person", representativeId, params, {staged: false, apply: () => {}})`. The `apply` callback is a no-op: the override lives in shared governance, not in Build's data, and only the Action writes it (`core/actions.js` calls `DC.resolution.reject` with the instance id). Build never writes an override itself: any outcome other than `applied` changes nothing (review F-19).

### 10.8 Purposes and Karlsruhe mode (F9)

Each rule's `note` (what it abstracts and what it leaves out) is listed in the open purpose panel; the seed's `legalBasisNote` is shown with any old "[to verify …]" placeholder stripped. Rules come from `seed.governance.purposeRules` (or `DC.purposes.rules()` when the core exposes it); the mode from `DC.purposes.enabled()` (toggle in the session strip). Build evaluates the rules that have an `incompatible: {data, session}` clause (R2) per **derived dataset**, not per transform, so `normalize_sources`, which copies each source on its own, is not flagged:

- the data purposes of a dataset are its manifest `purpose` plus purposes implied by its effective markings (`HEALTH` ⇒ `healthcare`);
- a dataset breaks the rule when one parent has a purpose in `incompatible.data` and another parent, or the dataset's own `purpose`, has a purpose in `incompatible.session`. In the current seeds `resolved_persons` (clinic data joined into the financial-crime person table), `ontology_entities` and `ontology_edges` break R2.

Build evaluates the rule text itself rather than calling `DC.purposes.check` on every render, so displaying the DAG never writes audit events. With the mode off, Pipelines and Markings show a one-line hint; with it on, the purpose panel (a `<details>` element: summary with the rule text, then one line per offending dataset and the seed's `legalBasisNote`) and the red badges. Nothing is blocked in Build: the pipeline has already run.

### 10.9 Discussion cards (spec §5.4)

`DC.ui.discussionCardsFor(surfaceId)` on Pipelines (`build.pipelines`, POL-INTEL) and Markings (`build.markings`, ICE ImmigrationOS/ELITE and NHS FDP), wrapped in `.build-discussions`, which restyles the core's markup for the black workspace (surface background, purple top rule, green kicker and links). Without the core helper, Build renders `seed.governance.discussions` itself (title, summary, questions, sources, disclaimer).

### 10.10 Retention clock (F12)

PHASE3_CONTRACT §4; honesty chip `build.retention` (Simplified). Computation in `js/retention.js` (`BuildRetention.compute(ctx, clockMs)`), rendering in `app.js` (`renderRetentionClock`, `renderRetentionSummary`, `renderRetentionOverview`).

- **Slider:** day steps from `asOf` − 3 years to `asOf` + 1 year, where `asOf` is the latest dataset `asOf` in the seed (2026-04-12 in both seeds). Presets: 3 years before, as of, +6 months, +1 year. Stored as `retentionOffset` (days) in the persisted UI state. Dragging (`input`) re-renders only `#ret-host`, so the slider survives; releasing commits, re-renders and logs one `retention.clock` event.
- **Date column per raw dataset:** `retentionDateField`/`dateField` if the seed declares one, else the first of `registered_on`, `timestamp`, `txn_ts`, `departure_ts`, `incorporation_date`, …, else the first date-typed field that is not a date of birth. The watchlist has none (only `dob`): the page says "No date column; retention cannot be applied", which is itself the teaching point.
- **Raw rows:** a sample row is *past retention* when `clock − date > retentionDays`; *not yet collected* when its date is after the clock. Each row gets a text tag in a leading **retention** column (the tag carries the meaning; grey strike-through, amber edge and italics only repeat it).
- **Derived datasets**, through lineage: single-source copies (`norm_*`) by `_source_row`; object datasets (`resolved_*`, `ontology_entities`) by each object's `lineage.sourceRows` and `fieldProvenance`; `ontology_edges` by each link's own date (`firstSeen`, `asOf`, `lastTxnTs`) against the retention of the raw dataset with the link's marking; `leads` by each component's `date` (or `asOf − ageDays`) against its source's raw retention. The page says "*n* rows still carry data past retention upstream", names the raw sources, tags those rows *carries expired data*, and lists datasets downstream of a raw dataset that still hold its expired rows. Datasets with no row lineage fall back to their raw ancestors' counts.
- **Counts are lower bounds** where only a sample is known: the seed ships about 20 rows per dataset, so the browser knows the dates of sampled rows and of dated links only. The page says "at least". In the starter seed, pings (180 days) expire first: at +6 months all sampled pings are past retention and 13 Persons, 13 ontology objects, every `OBSERVED_AT` link and 18 of the 24 leads still carry them.
- A **Discussion** line asks about deletion that never reaches copies; cards attached to `build.retention` are shown below it.

### 10.11 Leads in Build (F8)

PHASE3_CONTRACT §1 and §4. The `06 Build Leads` transform (`build_leads`) and the `leads` dataset need no special code on the Pipelines and Markings tabs: they are an ordinary transform and an ordinary derived dataset, inheriting OPEN, PII, TELECOM, HEALTH and LE-SENSITIVE through `markingProvenance`, and flagged by R2 in Karlsruhe mode (clinic data joined into a financial-crime output).

- **Leads view** (Datasets tab, `renderLeadsView`): rows come from `seed.leads.items` if present, else the dataset's `sampleRows`. Columns: retention tag, person (through the role's redaction), best address, stored score, score you can see, sources (marking badge, source, contribution) and newest age. Selecting a lead shows its formula with the numbers filled in: `DC.ui.leadFormula(lead, visibleComponents)` when the core has it, else a local table (`weight × exp(−ageDays / 365) = decay → contribution`, sum capped at 100).
- **Withheld components** are a marking badge and "1 source withheld": no dataset name, weight or address (the weights table would name the source). Redaction uses each component's full `markings` list (clinic `["PII", "HEALTH"]`), falling back to `marking`. In a lead's lineage, withheld components and source rows are counted by marking.
- **Per-role columns:** leads mix sources with different markings, so the dataset is shown component by component, as in Investigate, rather than withheld whole. A component whose marking the role cannot see is hatched (or "blocked by rule R2" in Karlsruhe mode with a law-enforcement session purpose). The row's top-level `address`, `lat`, `lon` and `score` are the all-markings view, so as soon as one component is withheld they are withheld too: the address column shows the best address among the visible components ("best of the sources you can see") and the score is recomputed from them. Rows are sorted by the visible score, because the stored order is itself the all-markings ranking. When the core's `leadFormula` is called for such a role it receives a copy of the lead without the all-markings fields. Tested: as DPO the namesake `person::g5510077` is the top lead with "41 Oak Lane, Birmingham"; as fin-analyst he is not top and "41 Oak Lane" appears nowhere in Build.
- **Lineage tab:** leads are listed under a **Leads** group after the objects (they are not ontology objects); a lead's page shows its properties (same redaction), the formula, and a tree from the lead through `06 Build Leads` to each component's source dataset with its marking, age and date.

## 12. Rendering model

The UI follows a full re-render strategy:

1. update state,
2. regenerate HTML via template strings,
3. replace the relevant region's `innerHTML`.

Acceptable because datasets are modest (≤1534 entities, ≤6000 edges in simulator) and the app is classroom-oriented.

- Contrast (fix round): every changed state is WCAG AA on black — expired rows `#c9c0c7` (11.1:1, no strike-through; the retention tag carries the meaning), not-yet-collected rows `--text-muted` (7.2:1), code line numbers `#8a8088` (5.2:1). Links are underlined at `0.32em` so underscores stay visible. The pipeline and markings DAGs sit in a `.scroll-wrap` that shows a green "More to the right →" cue (and "← more to the left") while columns are hidden, with a wider scrollbar.
- Dense layout: persistent left sidebar (240px), main pane, bottom inspector (Pipelines and Markings only); the Resolution tab uses a two-column main pane (table left, sticky merge explanation right; one column below 1,100px)
- Rule badges: red `#d93a3a` with the rule id written out (`R2`); merge decisions as text pills (`merged` green, `separate` outlined, `rejected by override` red); negative signal weights in light red
- Marking palette as CSS variables, light tints on black with black text on solid badges: `--mk-open #d6d6d6`, `--mk-pii #7db8ff`, `--mk-fin #ffc94d`, `--mk-telecom #4fd8c8`, `--mk-health #ff7b7b`, `--mk-le-sensitive #d39bff` (`--mk-le` alias, `--mk-unknown` fallback). The seed names the variable per marking (`governance.markings[].colour`). Colour never carries meaning alone: every marking is also a text badge, inherited badges are dashed outlines, withheld values are hatched with the marking named

## 14. Build and run

### 14.1 Build seed

```bash
python3 scripts/build_foundry_seed.py --output foundry-demo/seed.js
```

### 14.2 Serve demo

```bash
python3 -m http.server 8124        # from the repository root
# open http://127.0.0.1:8124/foundry-demo/
```

Serve the repository root: the app loads `../core/` and `../brand/`. Investigate (`/demo/`), Oversight (`/audit/`) and the glossary (`/glossary.html`) are then on the same origin and share the session, audit log and marking overrides.

### 14.3 Regenerate datasets

The Foundry demo reuses the synthetic data produced by the Gotham demo's generator:

```bash
python3 scripts/generate_synthetic_sources.py --profile starter   --output synthetic_data/starter
python3 scripts/generate_synthetic_sources.py --profile simulator --output synthetic_data/simulator
```

After regenerating, rebuild both seeds (the Gotham `demo/seed.js` and the Foundry `foundry-demo/seed.js`). `--seed` (default 20260401) only affects the clinic data; `--legacy-seed` (default 42) drives the Phase 0 files.

## 15. Validation approach

`bash scripts/check.sh` builds both seeds to a temp directory, runs `node --check` on both apps and the built seeds, and runs the pytest suite in `tests/` (Gotham/Foundry parity of entities, edges and `resolution`; no Person named after its ID; seed metadata, `resolution` validity, size under 10 MB; committed seeds up to date; governance block, object markings, dataset marking propagation and generator determinism). See `TECHNICAL_SPEC.md §23`.

There is no automated browser test suite.

## 16. Performance characteristics

### 16.1 Strengths

- no network round-trips after page load
- no backend dependency
- pipeline runs offline at build time, never in browser
- UI state persistence is minimal (no full ontology in localStorage, unlike Gotham demo)

### 16.2 Current constraints

- full HTML re-render on every state change
- sample rows are capped per-dataset; full inspection of large datasets is not provided
- DAG rendering is a fixed left-to-right flow rather than a real graph layout — adequate for 6 transforms, would not scale to dozens
- lineage payload duplicates source row references across fields; for the simulator dataset this contributes notably to seed.js size (~7 MB)

## 17. Security and privacy model

Identical to the Investigate app: all data is local synthetic data, no authentication, no multi-user separation beyond browser-local state. Roles, markings and Checkpoints are evaluated in the browser: they model access control for teaching and enforce nothing (the whole seed is readable in the developer tools; the honesty label `session.roles` says so). Acceptable for the classroom demo, not for production.

## 18. Known limitations

- no in-browser re-execution of transforms — pipeline runs offline only
- no schema-evolution tooling (cannot model what happens when a raw column type changes)
- no branching of the ontology
- no write-back from ontology to source systems
- purpose-based access control only as markings plus five roles; purpose rules that block joins are not yet modelled
- no real-time / streaming pipeline mode
- DAG layout is fixed; a true graph layout engine would be needed for larger pipelines
- transform code embedded in seed is plain text only (no syntax highlighting)
- lineage payload duplicates references; future versions could deduplicate via shared source-row pointers
- the retention clock only shows what would expire; there is no deletion step, and counts are lower bounds over the sampled rows

## 19. Extension points

### 19.1 Editable transforms

Port the pipeline framework to JS so transforms can be edited in the browser and re-run live. Doubles the JS surface area; deferred from v1.

### 19.2 Schema diff and stale-build indicators

Detect when a raw source schema has changed since the last build and surface the affected downstream datasets with amber "stale" badges. The build-status color palette is already in place in CSS.

### 19.3 Time-of-build versioning

Store a build manifest with hashes of source files and transform code; show which entities are affected when re-building.

### 19.4 Branch-and-merge

Allow forking the ontology, running a hypothetical transform change, and showing a diff against the main branch.

### 19.5 Data-subject view

A focused view that, given a real person's identifier, shows everything the system stores about them and where it came from — the user-facing complement to the analyst-facing Lineage tab. Pedagogically valuable for GDPR / data-rights teaching.

## 20. Relationship to the Gotham demo

This app and Investigate (`demo/`) share:

- the same synthetic source datasets (`synthetic_data/starter`, `synthetic_data/simulator`)
- the shared governance core (`core/`), the session (role), the audit log and marking overrides
- the same entity identity convention (`{type_lowercase}::{slug(external_key)}`)
- the same set of entity and relationship types

They deliberately differ in:

- audience (engineer/auditor vs. analyst)
- aesthetic (dark IDE vs. light analyst workspace)
- scope (build-side vs. consumption-side)
- persistence model (UI state only vs. full editable ontology)

Person resolution is shared: both `pipeline/02_resolve_persons.py` and `scripts/build_ontology_seed.py` use `pipeline/resolution.py`, and `tests/test_resolution_parity.py` checks that the two seeds have identical entity IDs and edge sets.

## 21. Summary

The Foundry Studio demo is a **static, framework-free, browser-based pipeline inspection demo** built around an explicit, executable transform DAG with end-to-end lineage capture. Its core design choices are:

- treat the pipeline as code, not configuration,
- treat every intermediate dataset as inspectable, not hidden,
- treat lineage as a first-class browser-side citizen, not an engineering-only artifact,
- preserve identity with the Gotham demo so the two apps describe one operational model,
- prefer transparent execution over hidden cleverness.

This makes it well suited for teaching how the *build side* of a Palantir-style system works at the architectural level, paired with the Gotham demo's coverage of the *consumption side*.
